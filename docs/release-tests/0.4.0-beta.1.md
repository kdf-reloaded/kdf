> on the 0.4.0-alpha.1 head and on fixes merged during the batch. They are recorded below; rows still

each one checked, on which build, and what came out of it.

## Builds and conventions

The conventions below are carried over from 0.3.0-beta.1; confirm them before the campaign.

**What SwapLab is.** SwapLab is the live test harness that runs Reloaded and reference nodes in isolated container stacks against real chains.

**Host.** One 256-core Linux host runs all nodes in containers. During the morning runs of 2026-11-05
its load average was about 265, from builds of other work; no timing condition came close to its
limit.

**Reference nodes.** Komodo DeFi Framework 2.6.0-beta ("K", netid 8762, also accepts 6133) and GLEEC KDF 3.0.0-beta ("G", netid 6133, rejects 8762). These are the official release binaries, run unchanged; their behavior is reported as counts and outcomes only. ### Row 1 — market survey

**Name:** Row 1, market survey: whether the 13 coins of the Electrum latency study of 2026-11-02
(CRD ch.38) still have live orders on the public network.

**Nodes:** one KDF Reloaded node on H, on the public seeds, with no coin activated.

**Conditions:** the mmrpc-2.0 `orderbook` asked for every pair against the quote coins KMD, BTC,
LTC, DOC, MARTY and RIN.

**What was tested:** that each of the study's 13 coins has at least one live pair.

**What happened:** 4,458 pairs asked, 627 live rows; 11 of the 13 coins have a live pair. CLC and RXD
have none, and their groups have no unused live coin, so both are dropped from the sample.

**Planned duration:** none set; it ran 7 min, 150 s of sync and a 228 s survey.

**Pass conditions:** each coin has at least one live pair; a coin without one is replaced within its
group, or dropped if the group has no unused live coin.

### Row 3 — L-DNS

**Name:** Row 3, L-DNS: the resolver modes of `dns_resolver` (PRs #216, #219; CRD ch.45 §45.6B,
T45.22).

**Nodes:** a Reloaded node and a Reloaded relay, both on H, and a lab DNS server that logs every query.

**Conditions:** private network; RIN as the main coin; a fresh database for each case. The node's own
system resolver points at the lab DNS server in every case. A packet capture records every packet the
node sends to ports 53 and 853.

**What was tested:** nine cases: the default (Google Public DNS), `"system"`, a fixed lab server, an
unreachable fixed server, the last known answer while no server answers, invalid values, the
activation of each coin family in fixed mode, a name handed out by a peer, and a name that does not
exist.

**What happened:** cases 1 to 7 and 9 behaved as specified. Case 8 cannot be created with Reloaded
peers only and moved to row 15.

**Planned duration:** 2 to 3 h; the full run took 72 min, plus about 40 min of single-case reruns.

**Pass conditions:** one start-up line names the mode; lookups go only to the chosen resolver; a name
that fails gives one warning, and the node runs on; an invalid value stops the start with an error
that names `dns_resolver`.

### Rows 4–8 — N1–N5, near-server spreading

**Name:** Rows 4–8, N1 to N5: Electrum reads spread only over the near servers (PR #215; CRD ch.38).

**Nodes:** one KDF Reloaded node per arm, fresh each time, with wallet W1, on a private lab network
that no outside taker reaches (netid 8762). The new build is H; the old one is 0.3.0-beta.1
(9f0ec1c83). N3d ran the build of PR #262 (0bef1c9f3) against the old build.

**Conditions:** 200 rounds per arm of `my_balance` and `setprice` at volume 1; each arm cancels all
orders before and after its loop. The lab coins file, with no `electrum_spread_*` settings. N1: RIN
with the six servers of the lab list. N2: RIN with an earlier list of three servers. N3: DOGE against
KMD, LTC and RIN, with its two servers, which slow a client's reads to 1 s once it sends too many.
N4 and N5: RIN with `electrum_server_order` set to `mixed` and to `measured`, on the new build only.
RIN is set against DOGE, KMD and LTC.

**What was tested:** that the loop is faster on the new build where some of a coin's servers are slow
(N1, N2), that it is not slower where both servers slow their reads (N3), and how the two other
server orders compare (N4, N5).

**What happened:** on RIN the loop took about a quarter (N1) and a third (N2) of the old build's
time. On DOGE it took about 11 % longer in each of three pairs, just above the limit of 10 %
(finding F6). N4 and N5 took the same time as the default order. A confirmation run (N3c) showed the
cause: on the new build with the near-server rule off, DOGE took the old build's time again. A run
on the fix (N3d), which keeps at least two servers in the turns, took the old build's time as well.
No arm had an error or a timeout.

**Planned duration:** about 25 min per row in the run plan. The eight counted loops took 18 min (09:47
to 10:05, 0.3 to 6 min each); with the extra N3 pairs and their pauses, the block ran 53 min (09:47
to 10:40). N3c ran from 15:16 to 15:53, and N3d from 01:33 to 02:12 on 2026-11-07.

**Pass conditions:**
- N1: the new build's loop time is at most 0.7 times the old build's.
- N2: at most 0.6 times.
- N3: at most 1.1 times, judged on the mean ratio over order-balanced pairs: at least one pair with
  each build first, with pauses between the arms. No other lab node holds DOGE server sessions during
  the run. The criterion was restated after the first pair (see Part 3).
- N4, N5: informative, no pass rule.
- N3c, the confirmation of F6, on the new build only: the default against
  `electrum_spread_near_factor` `0`, in two order-balanced pairs with a 3-minute pause before every
  arm. Fixed before the run: CONFIRMED if the ratio of factor 0 to the default is at most 0.95 and
  factor 0 lies within 3 % of the old build's 299.45 s; REFUTED if the ratio is at least 0.98.
- N3d, the fix for F6: the build of PR #262 against the old build, DOGE as in N3, in two
  order-balanced pairs with a 3-minute pause before every arm. Fixed before the run: PASS if the
  ratio of the fix to the old build is at most 1.03, the fix's loop lies within 290.5 to 308.4 s,
  and no arm has an error.

**Findings and history**
- **Cause (issue #252).** Since block 57,750, the BC2 chain appends a fork id to the digest of every
  signature, as replay protection. Both implementations sign the plain Bitcoin digest, which the
  chain no longer accepts, so neither can spend BC2 since that height. Corrected in the third batch:
  what the chain requires is its sighash suffix; a signature made with a fork id (hash-type byte
  0x43) is rejected (see
  [BC2 confirmation](#bc2-confirmation--signing-with-the-chains-sighash-suffix)).
- **Next.** Work in progress: a CRD rule with a signing option in the coins file, and the fix, are
  under way. The swap cells and the fix verification rows follow the fix. BC2 is not a beta
  blocker. Done since: the fix is PR #264, verified by the BC2 confirmation rows of the third
  batch.
