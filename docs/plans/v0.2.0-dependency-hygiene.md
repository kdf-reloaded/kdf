> **Status:** active. `dev` moved on to `0.3.0-alpha.1` (`8cf7820e7`) but this
> plan's advisory/hygiene tracking still applies — none of it is version-line
> specific. This plan tracks the security
> advisories currently *accepted* in [`deny.toml`](../../deny.toml) and the work
> needed to actually clear them. Update the matching row when an item lands;
> delete this file when every non-`upstream-blocked` row is done.

> cargo-deny pinned to `0.19.9`) fails on any advisory **not** in `deny.toml`'s
> `ignore` list. So the workflow for each item below is:
> **fix the dependency → remove its `RUSTSEC-…` line from `deny.toml` → the gate
> stays green.** Removing an ignore line is the definition of "done".

## Accepted advisories → remediation

Grouped exactly as in `deny.toml`. "RUSTSEC ID" is the line to delete once fixed.

### Risk-inheritance framework (added 2026-08-06)

Applies to every *upstream-blocked* row below (A, B, C). The principle,
articulated by the project owner: as long as reloaded consumes upstream
code (Gleec-maintained `KomodoPlatform` org repos, or an unrelated third
party's crate like the Solana SDK) **unmodified**, its security posture is
substantially shared with that upstream project — reloaded is relying on
the same architecture the upstream maintainers themselves ship and stand
behind. The moment reloaded **forks, vendors, or rewrites** that code,
responsibility for its security and maintenance shifts onto reloaded
permanently: every future advisory in that dependency then needs to be
tracked and re-ported locally, rather than arriving through a normal
upstream update.

That means fixing an upstream-blocked advisory locally (by forking) is only
worth it when the concrete threat justifies taking on that ongoing
maintenance. Otherwise: stay aligned with what upstream ships, accept the
`deny.toml` ignore line, and revisit for free the moment upstream fixes it
themselves (a tag bump, not a fork). This is a different calculus from
*reloaded-owned* code (rewrites like `kdf_chain`, or things reloaded already
chose to vendor/patch, like the Zcash `time-core` pin) — reloaded already
carries the maintenance burden there regardless, so fixing advisories in
that code has no *additional* cost and should be prioritized more readily.

Applied 2026-08-06: sections B and C reassessed and **deferred** under this
framework (both are DoS/availability-class or narrow-precondition issues,
not directly key-compromising for reloaded's actual usage — see each
section). Section A was already deferred this way.

### B. Solana SDK — *upstream-blocked (Solana Labs/Anza, unrelated to Gleec), deferred by choice*
Old `ed25519-dalek 1.x` / `curve25519-dalek 3.x` persist via `solana-keypair`
2.2.3 / `solana-signature` 2.3.0 (current Solana SDK 2.x, the newest major —
verified: `ed25519-dalek = "=1.0.1"` is an *exact* pin in both crates'
manifests, not a loose caret reloaded failed to bump). The libp2p-Noise path
to `curve25519-dalek 3.x` is gone now that the fork migration is merged, so
this is purely a Solana-side issue, unrelated to section A.

Per the risk-inheritance framework above, and checked against reloaded's
actual code (2026-08-06): `mm2src/coins/solana/solana_types.rs`'s
`generate_keypair_from_slice` always derives the keypair from a single
32-byte seed via `ed25519_dalek::SigningKey::from_bytes` →
`.to_keypair_bytes()`, so secret and public key are always paired/derived
together, never independently sourced. RUSTSEC-2022-0093's "double public
key signing oracle" attack requires a keypair reconstructed from a
public key and secret key sourced separately (e.g. an externally-supplied
public key paired with a locally-held secret) — that precondition doesn't
appear to be met anywhere in reloaded's Solana signing path. `curve25519-
dalek`'s timing-variability issue (RUSTSEC-2024-0344) is a local/co-located
side-channel concern, not practically remote-exploitable. **Deferred** —
same reasoning as section C: not worth forking Solana Labs/Anza's SDK for.
**Dedicated plan:** `docs/plans/solana-sdk-upgrade.md`.

### F. Dismissed as unreachable — *re-check when the surrounding code moves*

Two Dependabot alerts were dismissed on 2026-09-23 as `not_used` rather than as
accepted risk. That distinction matters: **neither is a judgement about the
advisory, it is a judgement about our call sites.** The vulnerable code is
compiled into the binary in both cases. It is simply never reached today. Each
dismissal is therefore only as true as one specific fact about our source, and
nothing in CI checks that fact — if it changes, the dismissal silently becomes
wrong and the Security tab will not tell us.

Both should be revisited, in priority order:

**F1. `yamux` 0.12.1 — GHSA-vxx9-2994-q338 (high).**
A crafted inbound Data frame with SYN set and a body over `DEFAULT_CREDIT`
panics the connection state machine (`remove(...).expect("stream not found")`),
remotely and without authentication.

- *Why it is not reachable:* `mm2src/mm2_p2p/src/atomicdex_behaviour.rs:1213`
  builds the transport with `libp2p::yamux::Config::default()`. In
  libp2p-yamux 0.44 that is `Either::Right(Config013)`
  (`muxers/yamux/src/lib.rs:226-229`), so the muxer we actually run is
  `yamux 0.13.10` — the *patched* version. The vulnerable `yamux 0.12.1` is in
  the lock only because libp2p-yamux 0.44 depends on both lines unconditionally.
- *What would invalidate it:* anything constructing the deprecated
  `yamux::Config::client()` / `::server()`, or calling
  `set_window_update_mode` / `set_receive_window_size` /
  `set_max_buffer_size` — every one of those is a `Config012`-only setter and
  silently switches the connection onto the vulnerable line. A libp2p bump that
  changes `Config::default()` does the same.
- *Real fix:* a libp2p-yamux that no longer depends on `yamux012` at all
  (upstream dropped it after 0.44). Falls out of the ch28 fork modernization;
  until then this is the only thing standing between us and a remote panic, and
  it is one line of unrelated-looking config away from being untrue.

**F2. `jsonwebtoken` 8.3.0 — GHSA-h395-gr6q-cpjc (medium).**
Type confusion in claim validation: a standard claim (`nbf`, `exp`) supplied
with the wrong JSON type is marked `FailedToParse`, which the validator treats
identically to `NotPresent` and skips — an authorization bypass for any caller
that validates a claim without also listing it in `required_spec_claims`.

- *Why it is not reachable:* it arrives only through `relay_rpc`
  (WalletConnect fork `k-0.1.3`). KDF mints and sends
  (`mm2src/kdf_walletconnect/src/lib.rs:918-926`, call site `:253`), and
  `relay_rpc` does its *signing* by hand with `data_encoding` +
  `ed25519_dalek::SigningKey::sign` (`relay_rpc/src/jwt.rs:106-121`) — no
  `jsonwebtoken` involvement. The crate is linked in **exclusively** through
  `VerifyableClaims::decode` (`jwt.rs:260`, `jsonwebtoken::crypto::verify` at
  `:190-195`), whose only callers in the whole tree are upstream's own unit
  tests (`jwt.rs:273-285`).
- *What would invalidate it:* any use of `relay_rpc`'s HTTP client
  (`relay_client::http`, used for `watchRegister`/`watchUnregister`) or any code
  that begins verifying a relay-supplied JWT. We currently use only the
  websocket client.
- *Real fix:* bump the WalletConnect fork to `jsonwebtoken` 10.3+. Folds into
  `docs/plans/walletconnect-fork-upgrade.md`, which already has to touch that
  fork for the accepted `tungstenite` advisory (section C) — do both in one pass.

Note for whoever picks these up: because both are dismissed rather than ignored
in `deny.toml`, neither the cargo-deny job nor the `dependabot-alerts` job will
ever go red for them again. Reopening the alert on the Security tab is the way
to put them back in front of CI.

### G. `async-std` 1.6.2 — *reloaded-owned, blocked on a swap-shutdown code change*

`async-std 1.6.2` is a direct dependency of `common`, `coins` and `mm2_main`, and
is the reason `crossbeam-utils 0.7.2` (RUSTSEC-2022-0041 / GHSA-qc84-gqf4-9926,
Dependabot alert #7) is in the tree. Dismissed as `tolerable_risk` on
2026-09-23: the advisory is `informational = unsound` and affects only
`AtomicCell<{i,u}64>` `fetch_*` on 32-bit targets that have `Atomic{I,U}64`, so
64-bit targets are unaffected outright — but armv7 and wasm32 are both shipped,
so "unaffected" is not the same as "irrelevant here".

This is **not** upstream-blocked. It is blocked on our own code:

- `async_std::sync::channel` was removed in async-std 1.9. It is still used at
  `mm2src/mm2_main/src/lp_swap.rs:59` (import), `:341` (the
  `shutdown_rx: async_std_sync::Receiver<()>` field) and `:360` (construction).
- The replacement is `async_std::channel::bounded`, backed by `async-channel`.
  `Sender::send` gains a `Result`, and — the part that actually needs care —
  `Receiver::recv` returns `Result<T, RecvError>` instead of `Option<T>`. That
  return type is consumed in the `select!` arms of both swap loops:
  `maker_swap.rs:2042`/`:2104` and `taker_swap.rs:374`/`:430`, each doing
  `shutdown_rx.clone()` then `shutdown_rx.recv().fuse()`.

So roughly six call sites and a small diff, but it is live swap-shutdown code
and there is no end-to-end swap test to catch a regression in it — treat it as a
behaviour change to be reviewed, not a mechanical bump. A first attempt during
the 2026-09-23 triage bumped async-std to 1.13.2, broke the build on exactly
these call sites, and was reverted.

Doing it clears alert #7 and lets the correction block in `deny.toml` go.

  `"0.8"`; `SegQueue::pop()` changed from `Result<T, PopError>` to

  and removed a second, completely unused `crossbeam = "0.7"` pin in
  `mm2src/mm2_main/Cargo.toml` (zero call sites, verified by grep) while

- **Legacy WASM process-log tail.** `PROCESS_LOG_TAIL`, `TAIL_CUR`, and

  They have no remaining Rust, JavaScript, or test consumer in this repository

  during beta validation because `static mut` creates an unnecessary Rust 2024
  compatibility and future threaded-WASM safety risk. Before the production
  release, delete the commented implementation (recommended), or replace it
  with a safe owned ring buffer if a real consumer is identified. Leaving the
  commented implementation in the production release is not an accepted final
  state.

## Guardrails

- **Branching:** large/risky items (secp256k1 migration, Solana SDK bump,
  WalletConnect fork bump, Lightning LDK uplift) each get their own feature
  branch off `dev`, named to match their plan doc
  (`dep/secp256k1-0.29`, `dep/solana-sdk-2.x`, `dep/walletconnect-tungstenite`,
  `dep/lightning-ldk-uplift`). Small, mechanical, independently-reversible
  bumps (the "Compiler-warning follow-up" items, patch/point releases,
  single-manifest renames) are bundled under one shared `dep-hygiene` branch
  rather than a branch each — split out of it only if one turns out to need
  its own regression pass. `--no-ff -S` merge either way.
- Never merge a dependency bump without: `cargo build --release` + the affected
  crate's tests + clippy on the changed crate(s). Funds-touching crates
  (coins, db_common) additionally need their unit/integration tests.
- After any Cargo.lock change, `cargo deny check advisories` must stay green
  (the CI gate enforces this on PR).
- WASM-affecting changes: run the applicable local
  `--target wasm32-unknown-unknown` checks and retain CI as the complete
  cross-platform gate. For anything claiming to fix the secp256k1 WASM
  blocker specifically, `cargo check` is not sufficient proof — use
  `cargo build --target wasm32-unknown-unknown -p mm2_bin_lib --lib` (the
  actual link step) per `secp256k1-migration.md`.
- Commit each item once it independently builds/tests/lints clean; don't
  batch unrelated dependency bumps into one commit even on a shared branch.
